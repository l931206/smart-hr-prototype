# Smart HR AI 功能規劃

## 目標

AI 不新增成另一個獨立頁面，而是成為員工、主管與管理者工作台的主要操作入口。AI 只協助理解需求、查詢及準備操作；任何會改變資料的動作，都必須先顯示結構化確認內容，再由使用者明確確認。

## 共通安全原則

1. AI 使用目前登入者的 Token 呼叫既有 API，不得繞過後端權限。
2. 後端仍是唯一權限判斷來源；前端隱藏按鈕不代表授權。
3. 建立、核准、退回、撤回、停用等寫入操作一律要二次確認。
4. 回覆只使用登入者原本就能透過 API 讀取的資料。
5. 每次 AI 寫入操作都寫入 `AuditLog`，保留操作者、資料類型、編號與時間。
6. 不把附件、密碼、Token 或完整個資送到未核准的外部模型服務。

## 員工情境

### 對話式請假

使用者可以輸入：「我下週一下午請特休，私人行程。」

AI 將文字轉成草稿：

```json
{
  "leave_type": "特休假",
  "start_date": "2026-08-17",
  "end_date": "2026-08-17",
  "start_time": "下午",
  "end_time": "下午",
  "reason": "私人行程"
}
```

送出前顯示假別、日期、時段、工作日天數、剩餘額度、附件規則及審核主管。使用者按「確認送出」後，才呼叫 `POST /api/leave-requests/`。

### 人資問答

可回答剩餘假期、請假狀態、最近公告與通知。第一階段只查詢結構化 API；公司規章文件完成整理後，再加入有來源標示的文件檢索。

## 主管情境

### 今日決策摘要

主管工作台優先顯示：

- 待審核請假與額度是否足夠。
- 今日晚到通知。
- 今日已核准請假人員。
- 需要主管處理的異常或缺少附件資料。

AI 可以摘要，但核准與退回仍必須由主管逐筆確認，不允許自動大量核准。

## 管理者情境

### 自然語言查詢

範例：「列出營運部所有在職主管」、「找出尚未設定直屬主管的員工」。AI 將問題轉成 API 篩選條件，先顯示查詢條件，再回傳清單。若要停用或修改資料，仍需進入確認流程。

## 建議技術流程

```text
使用者輸入
  → 意圖與欄位解析
  → 後端依登入 Token 取得可讀資料
  → 顯示草稿／查詢條件與來源
  → 使用者確認（只有寫入操作需要）
  → 呼叫既有 REST API
  → 寫入 AuditLog
  → 顯示完成通知
```

## 分階段實作

1. 先完成「對話產生請假草稿」，只解析不送出。
2. 串接現有假別、餘額與主管 API，產生確認卡片。
3. 使用者確認後呼叫既有請假 API。
4. 加入主管今日摘要與管理者自然語言查詢。
5. 最後才評估公司規章文件檢索與正式 AI 模型服務。

## 驗收條件

- AI 無法查到角色原本無權查看的資料。
- 未按確認時，資料庫不產生任何異動。
- 日期、工作日、半天／小時與剩餘額度使用後端計算結果。
- 所有寫入結果可在系統操作紀錄追查。
- AI 服務暫時不可用時，原本的表單與清單功能仍可正常使用。
